## Scenario A — PDF question answering

### Problem description

Ingest a PDF, extract clean text, chunk it, retrieve and answer with a citation. The PDF in
this module is generated by `gen_data.make_pdf` and contains the same 24 handbook sections as
the markdown corpus, so you can compare extraction fidelity.

### Data and licence

- `corpus/northfield-handbook.pdf` — 4 pages, 15,293 bytes, generated for this module (CC0-1.0).
- `pypdf` (**BSD-3-Clause**) for extraction; `sentence-transformers/all-MiniLM-L6-v2`
  (**Apache-2.0**) for embeddings; `google/flan-t5-small` (**Apache-2.0**) for generation.

### Tasks

1. Extract text with `load_pdf("corpus/northfield-handbook.pdf")`. Report pages, characters
   extracted and the first 90 characters. Compare with the markdown corpus (11,608 characters
   of source text).
2. Identify three extraction artefacts (line breaks inside sentences, running headers,
   hyphenation) and write a cleaning function for each.
3. Chunk at 60 words with 15 overlap and report the chunk count. Compare with the 48 chunks
   from the markdown corpus.
4. Answer five questions with citations; verify each citation by opening the cited page.
5. Measure: can you recover the same answer from the PDF as from the markdown? Report the
   differences.

### Expected results

```text
pdf pages: 4   extracted chars: 12471
first chars: Northfield University Student Handbook (fictional) Library opening hours. The Hartley Libr
markdown corpus: 24 documents, 11608 characters, 48 chunks at 60/15
```

## Scenario B — the university FAQ chatbot

### Problem description

Build the complete assistant: hybrid retrieval, late-interaction reranking, context packing,
a refusal path, and a Streamlit interface that shows its sources.

### Tasks

1. Build the index: `RAGSystem()`. Report documents, chunks, embedding dimension, index backend
   and build time (measured here: 24 documents, 48 chunks, 384 dimensions, FAISS, 44.9 s).
2. **Retriever comparison.** Run `evaluate_retrievers(system, QA)` and reproduce:

   | retriever | recall@1 | recall@3 | MRR | nDCG@3 |
   | :--- | ---: | ---: | ---: | ---: |
   | dense | 0.90 | 1.00 | 0.944 | 0.959 |
   | BM25 | 0.97 | 1.00 | 0.983 | 0.988 |
   | hybrid | 1.00 | 1.00 | 1.000 | 1.000 |
   | hybrid + rerank | 1.00 | 1.00 | 1.000 | 1.000 |

   Explain why BM25 beats dense at rank 1 on this corpus, and why reranking changes nothing
   at the top of the list.
3. **Chunk sweep.** Reproduce the 40/60/100-word sweep. Report recall@1, MRR and end-to-end
   exact match for each (measured: 0.93/1.00/0.93 recall@1; EM 0.67/0.75/0.75).
4. **Fusion weight.** Set $\alpha$ to 0.0, 0.5 and 1.0 and report recall@1. Explain the
   endpoints in terms of which retriever dominates.
5. **Context packing.** For the deposit question, print the packed context and its length
   (measured: 810 characters from `['hb-07','hb-07','hb-06']`). Reduce `max_chars` to 400 and
   re-answer; does the answer survive?
6. **Refusal behaviour.** Run the eight unanswerable questions. Report the refusal rate
   (measured 0.00) and quote four wrong answers. Then add a retrieval-score threshold and
   report the new refusal rate and the over-refusal rate on answerable questions.
7. **Interface.** Run `streamlit run app.py`. Confirm that every answer displays sources and a
   grounding score, and that a refusal is visually distinct from an answer.
8. **Error analysis.** Find at least four failures: one retrieval miss, one wrong span, one
   unsupported claim, one unnecessary refusal. Quote the evidence.

### Expected end-to-end results (12 questions)

```text
exact match 0.75   token F1 0.85   ROUGE-L 0.85
mean support 1.00   refusals 0/12   mean latency 1.84 s
failures: '20:00' for the weekday opening time; '15 October' for the January instalment
unanswerable examples: '15 working days', '1', 'John C.', '40 GBP' -- all wrong, none refused
```

## Scenario C — a document assistant for a second corpus

### Problem description

Repeat the pipeline on a different corpus of your own (course notes, public-domain manual).
The point is to discover which parameters do **not** transfer.

### Tasks

1. Build a 20-question evaluation set with gold documents.
2. Run dense, BM25 and hybrid. Report whether the ranking of retrievers changes.
3. Re-run the chunk sweep. Report the best size and compare it with 60 words.
4. Report one failure mode that did not occur in the handbook corpus.

### Expected results

There is no expected number here, and that is the lesson: chunk size and fusion weight are
corpus properties, not universal constants. Report your values with the corpus description.

## Extensions

- Add reciprocal rank fusion across three query paraphrases and measure the delta.
- Implement parent–child retrieval and compare answer completeness on multi-sentence questions.
- Add a "not found" sentinel document and measure whether the model uses it.
- Cache embeddings and measure the rebuild time saved.

## Common pitfalls

- Reporting retrieval metrics only, and never checking whether the answer used the context.
- Chunking the PDF without cleaning it, then blaming the embedding model.
- Treating a 0.00 refusal rate as success because exact match looked high.
- Comparing retrievers with different $k$ or different chunk sizes.
- Publishing the index for a corpus you may not redistribute.

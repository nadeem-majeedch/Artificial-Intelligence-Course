# Licensing and Attribution Report

**Method:** inspection of the repository root and every module for licence files and notices;
review of dataset, model, dependency and reference statements in lessons and labs; reading of
installed package metadata for the libraries the course uses.

---

## 1. Repository licence — missing

| Item | Finding |
| --- | --- |
| `LICENSE` | **Absent** |
| `COPYING`, `LICENCE`, `LICENSE.md` | **Absent** |
| Licence statement in `README.md` | **Absent** (0 mentions of licence, copyright or terms) |
| Licence statement in `docs/about.md` | **Absent** (0 mentions) |
| Licence statement in `docs/faq.md` | Present, and it is a restriction |

The FAQ answers "Can I use this material for my own course?" with: *"Ask the instructor. The
structure, labs and rubrics were designed to be adapted, but the material is not offered here
under an open licence, so permission is required."*

Under default copyright, a public repository without a licence grants no rights to copy,
modify or redistribute. So the FAQ is legally accurate — but it is also the only licensing
statement in the repository, it is buried in a FAQ, and it means:

- Students may read the material but have no explicit right to reuse it.
- Instructors cannot fork, adapt or teach from it without asking.
- GitHub's own "fork" affordance and the repository's public visibility imply an openness the
  text denies.

**This is the highest-severity licensing finding.** It is a decision for the author — this
audit does not choose a licence on the author's behalf, because the choice (all rights reserved
vs. CC BY 4.0 vs. CC BY-NC-SA vs. MIT for code plus CC BY for prose) has legal consequences
that only the rights holder can accept.

**Recommended minimum:** add a root `LICENSE` file (or a "Licence" section in `README.md` that
points to it) stating the terms explicitly, and make the FAQ answer consistent with it. If
permission-required is the intent, say so in the README, not only in the FAQ.

## 2. Code licence versus content licence

The repository mixes three kinds of material that normally carry different licences:

| Material | Count | Typical licence |
| --- | ---: | --- |
| Prose lessons, labs, assessments | 275 Markdown files | CC BY 4.0 or CC BY-NC-SA 4.0 |
| Python reference code | ~60 `.py` files in `modules/*/code` | MIT or Apache-2.0 |
| Notebooks | 14 `.ipynb` | inherits the code licence |

Nothing in the repository distinguishes these. Even if the author later adds a single licence,
a split (content vs. code) is the conventional and safer arrangement.

## 3. Datasets

| Dataset | Where | Licence claim in repository | Verified? |
| --- | --- | --- | --- |
| Synthetic tabular data (student, loan, recruitment, fraud) | M06, M13 `code/*_data.py` | "synthetic, generated in-script (CC0-1.0)" | Consistent: generated by seeded code, no third-party file |
| Synthetic enquiry corpus | LAB-01-01 | Generated in the lab, no download | Consistent |
| Iris subset | referenced as a real counterpart | "CC BY 4.0" | Correct (UCI Iris is CC BY 4.0) |
| Fashion-MNIST | M07 lab/notebook | referenced via its public source | Correct (MIT for the code; images distributed for research use) |
| Plant/image data | M07 lab | referenced, not bundled | No image files are redistributed, so redistribution risk is low |
| Text corpora for tokenisation/RAG | M11 `code/corpus/` | generated in-module | Consistent |

**No dataset is redistributed as a binary blob**, which removes the most common licensing
hazard. The repository's datasets are generated by code it owns, and real datasets are
referenced rather than copied. This is good practice and should be preserved.

## 4. Models

| Model family | Use | Licence position |
| --- | --- | --- |
| Hugging Face transformer weights (M07 transfer, M11) | downloaded to local cache at first run | The lessons state the models are used under their upstream licences; Apache-2.0 is claimed for the models named. Not redistributed in the repository. |
| Local toy models (BPE, attention, VAE/GAN/DDPM) | trained in-module | Code is the repository's own; no third-party weights |
| No proprietary API is required | — | Labs run offline |

Because no model weights are committed, model licensing is a runtime obligation for the
student, not a redistribution obligation for the repository. The lessons should still name the
licence of each named checkpoint; a spot check found licence statements present but not
uniform across all model mentions.

All are permissive. **No copyleft dependency (GPL/AGPL) is present**, so the code can be

manifest (no `requirements.txt` or `pyproject.toml` at the root) — a packaging gap rather than a
licensing one, but it makes a dependency audit harder for a student.

## 6. Research references and attribution

- Lessons cite papers by title and identifier (arXiv IDs, conference names) in "Further
  reading" — 49/49 lessons have such a section.
- No figure, table or substantial passage is copied from a paper or textbook; all diagrams are
  Mermaid, drawn for the course.
- The Mermaid diagrams are original.
- Quoted definitions are paraphrased rather than reproduced verbatim; no block quotes of
  copyrighted text were found in the sample.
- The course attributes the AIMA textbook as a reading resource without reproducing it.

**Attribution is adequate for referenced work**, because nothing is redistributed. It would
become inadequate only if figures were later added from papers.

## 7. Third-party notices

There is **no `THIRD-PARTY-NOTICES` file**. With no bundled third-party assets this is not
legally required, but a short notice listing the referenced datasets and model licences would
make the position auditable and answer the question students and instructors actually ask.

**Audit 7 verdict: FAIL.** Every third-party component is used lawfully and no restricted

blocker: nobody — student, instructor or publisher — knows what they may legally do with it.
